The monitor's decisions in LangSmith and Langfuse

Everything the monitor does already reaches a trace, but as raw model calls and a state update buried in a node's output. This plan gives each monitored step its own named spans, so a trace shows what was judged, how suspicious it was, and what the protocol did.

  • Any LangChain tracerLangSmith, Langfuse and anything else built on LangChain callbacks. No new dependency, no vendor code in part 1.
  • FilterableFind every halted or flagged step with one filter, in both tools, without part 2.
  • Streams unchangedThe message, update and custom streams stay byte for byte the same; only astream_events gains the spans.
  • Microseconds5 to 8 µs per span with no tracer attached, 30 to 45 µs with one. Nothing to turn off.

Built on two research notes in docs/plans/monitor-tracing/research/: LangChain's callback internals, with a prototype run under invoke and ainvoke, and how LangSmith and Langfuse record and show runs, probed against the real SDKs offline.

Today and after

The spans

Names are fixed and few, so both tools can filter and count by name. Everything that varies goes in metadata, which both show next to the span. Every metadata key is flat and starts with monitor_, so it never collides with LangGraph's or LangSmith's own keys.

Why fixed names: a name like monitor[main] step 3 would make every span unique, which breaks filtering by name in both tools, and any name containing "agent" makes Langfuse type the span as an agent. Why a separate decision span: a span's tags cannot change after it starts, and the step span has to start before the samples nest under it. A halt is a decision, not an error, so it never marks a span red; only a monitor that fails does.

How it works

The spans are opened by hand through the callback manager of the node that is running, the same one the agent's model calls use. Model calls made inside a span become its children, because the span's child manager goes on the config those calls inherit. It is the same mechanism the no-stream block from PR #40 already uses.

Pseudocode

_langchain.py · the only module that touches callback managers
@dataclass
class TracedRun:
    """What a traced block reports before its span closes."""

    outputs: dict[str, TraceValue] = field(default_factory=dict)
    inputs_at_end: dict[str, TraceValue] | None = None


@asynccontextmanager
async def open_traced_run(*, name: str, inputs, metadata, tags) -> AsyncIterator[TracedRun]:
    """Open a span under the running node; model calls inside the block become its children."""
    config = ensure_config()
    callback_manager = read_node_callback_manager(config)   # the node's own, so Langfuse keeps one trace
    if not callback_manager.handlers:
        yield TracedRun()                                    # nothing listens: no span at all
        return
    callback_manager.add_metadata(metadata, inherit=False)
    callback_manager.add_tags(tags, inherit=False)
    run_manager = await callback_manager.on_chain_start(None, inputs, name=name, run_id=uuid4())
    token = var_child_runnable_config.set(patch_config(config, callbacks=run_manager.get_child()))
    traced_run = TracedRun()
    try:
        yield traced_run
    except BaseException as error:                           # cancellation included
        await run_manager.on_chain_error(error, inputs=traced_run.inputs_at_end)
        raise
    else:
        await run_manager.on_chain_end(traced_run.outputs, inputs=traced_run.inputs_at_end)
    finally:
        var_child_runnable_config.reset(token)

middleware.py · the step and decision spans
async def awrap_model_call(self, request, handler):
    step_metadata = self.build_span_metadata(request, step_number=step_number)
    async with open_traced_run(name="monitor step", inputs={}, metadata=step_metadata, tags=["monitor"]) as step_span:
        step = AsyncPendingStep(..., span_metadata=step_metadata)
        with hide_model_calls_from_message_stream():
            decision = await self.protocol.decide(step)      # judgement spans open inside draw_sample
        record = self.build_step_record(decision, step_number=step_number)
        async with open_traced_run(
            name="monitor decision",
            inputs={},
            metadata={**step_metadata, **build_decision_metadata(record)},
            tags=["monitor", f"monitor:{record['outcome']}", *(["monitor:flagged"] if record["flagged"] else [])],
        ) as decision_span:
            decision_span.outputs = build_decision_outputs(record)
        step_span.outputs = build_step_outputs(record)
        step_span.inputs_at_end = build_step_inputs(record)
        return self.commit(request, record=record, decision=decision)

The research found two upstream problems that affect traces today, with or without these spans. They go to #27 for triage, not into the repository.

Decisions

  1. 1. Span names

    RecommendedFixed names (monitor step, monitor judgement, monitor classifier, monitor decision), with agent and step in metadata. Filtering by name works in both tools.
    AlternativeDescriptive names such as monitor[main] step 3. Easier to read in a tree, harder to filter, and an agent name containing "agent" confuses Langfuse.

  2. 2. Outcome tags

    RecommendedA short monitor decision span tagged with the outcome, so halted and flagged steps are filterable without part 2.
    AlternativeKeep the outcome only in the step span's outputs, one span fewer, and leave filtering to part 2.

  3. 3. The Decisions API call

    RecommendedA plain span, like the others. It never looks like the agent's own tool or model call in astream_events.
    AlternativeA model-call span, as the TypeSafe classifier does, so Langfuse shows it as a generation with the model name.

  4. 4. Proposal text in the spans

    RecommendedThe step span carries the proposed step, so it reads on its own; each sample's text stays on its model call, as today. Both tools can mask inputs for users who need it.
    AlternativeNo proposal text in any monitor span, for smaller traces.

Part 2: scores, after 0.1.0

Scores make suspicion numeric and chartable. The research recommends a core listener interface with no vendor imports, and one extra per tool.

ToolHowWatch out for
LangSmith, [langsmith]Feedback on the step span, written in process through the user's own client: monitor_suspicion, monitor_outcome, monitor_flagged, with the reason as commentIts client extends a trace's retention by default, which moves every monitored trace to paid storage; the exporter turns that off unless you opt in
Langfuse, [langfuse]Scores written after the run: find each step by monitor_step_id through the observations API, then attach the score to that exact observationNo public API maps a LangChain run to a Langfuse observation while the run is going, so writing scores during the run can land on another request's trace
